# Git it

**Загрузите проект в GitHub — без командной строки, без `git init`, без «а что такое remote».**

Перетащите папку (или ZIP) в браузер, выберите репозиторий — Git it соберёт из файлов настоящие коммиты
через GitHub API и покажет, что происходит на каждом шаге.

```
   ┌──────────────────┐        ┌──────────────────┐        ┌────────────────────────────┐
   │  папка или ZIP   │  ───►  │   Git it в брау  │  ───►  │  GitHub:  1…N коммитов     │
   │  my-project/     │        │  отбор файлов    │        │  репозиторий готов         │
   └──────────────────┘        └──────────────────┘        └────────────────────────────┘
```

## Первый запуск

Заход на сайт открывает **белую заставку**: из пустоты прорисовывается логотип Git it, из него «выезжает»
надпись, а под словом **it** побуквенно появляется слоган «залить проект в GitHub — легко и просто».
Сцена занимает около трёх секунд, её можно пропустить кликом, клавишей или прокруткой; при системной настройке
«уменьшить движение» она показывается сразу. Дальше — экран **«О проекте»**: что делает Git it, как устроены четыре шага и что
происходит с вашими файлами. Дальше — кнопка **«Начать»**:

- соглашение ещё не принято → открывается **лицензионное соглашение** и его нужно прочитать;
- соглашение уже принято (та же версия) → сразу открывается рабочий экран, а перечитать текст можно
  по ссылке в подвале.

Соглашение (версия 1.0, 13 разделов, ~1200 слов) нужно именно **прочитать**: кнопка «Принимаю соглашение»
разблокируется только после того, как текст прокручен до конца — просто поставить галочку не получится.
Прогресс чтения показан процентами. Отметка о принятии (версия + дата) сохраняется в браузере; при выпуске
новой версии соглашения приложение попросит ознакомиться с ней заново.

Текст соглашения доступен в приложении, в файле [AGREEMENT.md](AGREEMENT.md) и по ссылке в подвале страницы.
Тест `src/lib/agreement.test.ts` следит, чтобы текст в коде и в `AGREEMENT.md` не расходились.

## Что умеет

- **Папка, ZIP или отдельные файлы.** Перетаскивание (`drag & drop`), обычный выбор каталога и разбор ZIP-архивов —
  включая ZIP64 и кириллические имена файлов.
- **Не тащит мусор.** `node_modules`, `.git`, `dist`, кэши, `.env`, `*.pem` и прочее исключаются автоматически —
  по тем же правилам, что и в `.gitignore`. Правила можно дополнить своими прямо в интерфейсе.
- **Понятный отбор файлов.** Дерево проекта с поиском, счётчиками, галочками по файлам и каталогам и бейджами
  «исключён» — ничего не происходит «за спиной».
- **Большие проекты — несколькими коммитами.** Файлы режутся на пачки (по умолчанию 10 000 файлов и 400 МБ на
  коммит, лимиты настраиваются) и выгружаются отдельными коммитами: «Выгрузка проекта — часть 1 из 3». Обрыв
  загрузки не отменяет уже созданные коммиты, а прогресс показывает, какая часть идёт сейчас.
- **Управление прежними файлами.** При выгрузке частями можно дополнять репозиторий (прежние файлы остаются)
  либо приводить ветку ровно к содержимому проекта — без переписывания истории.
- **Файлы больше 100 МБ не ломают выгрузку.** GitHub через API такие файлы не принимает — это жёсткое ограничение
  сервиса, а не приложения. Git it предупреждает до отправки, перечисляет такие файлы с размерами, даёт выбор
  (пропустить и залить остальное или остановиться с ошибкой) и показывает в отчёте, что именно не уехало.
  Для таких файлов в интерфейсе есть инструкция про Git LFS.
- **Повторная загрузка почти мгновенная.** Содержимое сравнивается по git-хешу (тем самым, что считает
  `git hash-object`), поэтому неизменившиеся файлы не передаются заново. Если менять нечего — пустой коммит не
  создаётся вообще.
- **Умеет больше, чем «залить».** Создать новый репозиторий (личный или в организации) с нужной видимостью
  и описанием, залить в существующий и в конкретную ветку, положить проект в подпапку репозитория.
- **Разбор ошибок по-человечески.** Нет прав, истёк токен, закончился лимит запросов, файл слишком большой —
  вместо кода ответа показывается объяснение и что делать.
- **Тёмная и светлая темы**, адаптивная вёрстка, аккуратный прогресс со скоростью и оставшимся временем.

## Безопасность

У Git it **нет бэкенда** — это статическая страница. Токен доступа:

- хранится в `localStorage` вашего браузера (и никогда не уходит на сторонние серверы);
- передаётся только на `api.github.com` по HTTPS;
- удаляется кнопкой «Отключить» рядом с аккаунтом.

Ваш код тоже нигде не сохраняется: файлы читаются локально и уходят прямо в GitHub.

## Быстрый старт

```bash
npm install --legacy-peer-deps   # npm 10 спотыкается на резолве пиров vitest
npm run dev                      # http://localhost:5173
```

Дальше:

1. Прочитайте и примите лицензионное соглашение.
2. Нажмите «Войти в GitHub» — Git it предложит готовую ссылку на создание токена
   (`github.com/settings/tokens/new?scopes=repo,workflow`).
3. Перетащите папку с проектом. Git it покажет список файлов и исключит лишнее.
4. Выберите репозиторий и нажмите «Загрузить в GitHub».

**Токен классический (`ghp_…`)** — нужны права `repo` (доступ к репозиториям) и `workflow` (если в проекте есть
`.github/workflows`). **Токен fine-grained (`github_pat_…`)** — «Contents: Read and write», «Administration: Read and write»
и «Metadata: Read».

## Как это устроено

```
src/
├─ App.tsx                 сценарий целиком: онбординг, шаги, состояние
├─ components/
│  ├─ WelcomeScreen.tsx    экран «о проекте» с кнопкой «Начать»
│  ├─ AgreementScreen.tsx  соглашение с обязательным дочитыванием
│  ├─ DropZone.tsx         импорт папки, ZIP и файлов
│  ├─ FileTree.tsx         дерево файлов с отбором
│  ├─ RepoPicker.tsx       выбор репозитория, владельца и ветки
│  ├─ PublishPanel.tsx     план выгрузки, большие файлы, настройки коммита
│  └─ ProgressPanel.tsx    прогресс по частям и экран результата
├─ hooks/
│  ├─ useGitHub.ts         авторизация, список репозиториев и организаций
│  └─ usePublish.ts        прогресс загрузки, настройки, тема
└─ lib/
   ├─ github.ts            REST-клиент: blobs → trees → commit → ref, пачки коммитов
   ├─ gitblob.ts           SHA-1 git-объекта (сравнение содержимого)
   ├─ ignore.ts            матчер правил в стиле .gitignore
   ├─ project.ts           модель проекта и импорт из папки/ZIP
   ├─ zip.ts               читатель ZIP (EOCD, ZIP64, deflate) без зависимостей
   ├─ agreement.ts         текст соглашения, версия и отметка о принятии
   ├─ format.ts            форматирование размеров, чисел, путей
   └─ storage.ts           безопасная обёртка над localStorage
```

Публикация идёт ровно по шагам git-объектов:

1. `POST /repos/{owner}/{repo}/git/blobs` — содержимое новых и изменившихся файлов (до 6 параллельно).
2. `POST /repos/{owner}/{repo}/git/trees` — структура каталогов, батчами по 1000 записей.
3. `POST /repos/{owner}/{repo}/git/commits` — коммит со ссылкой на предыдущий.
4. `POST /repos/{owner}/{repo}/git/refs` (или `PATCH`) — ветка переводится на новый коммит.

При выгрузке частями шаги 1–4 повторяются для каждой пачки, причём каждая следующая опирается на дерево
предыдущей (`base_tree`), поэтому файлы ранних частей не теряются.

## Ограничения

- **Один файл больше 100 МБ GitHub через API не принимает — ни одним коммитом, ни частями.** Это ограничение
  сервиса: такие файлы Git it пропускает (с отчётом и списком) либо останавливает выгрузку — по вашему выбору.
  Для них нужен Git LFS или обычный git-клиент; инструкция есть прямо в интерфейсе.
- Лимит GitHub API — 5000 запросов в час на токен; при повторных прогонах лучше оставлять включённым
  «Не отправлять файлы повторно».
- Выгрузка **добавляет и обновляет** файлы; удаление файлов из ветки включается отдельным переключателем при
  выгрузке частями.
- Приватные ZIP с паролем и архивы с bzip2/LZMA не читаются (только `store` и `deflate`) — об этом честно
  сообщается при импорте.
